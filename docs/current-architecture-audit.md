# 当前架构审计

## 已落地的边界

- `data/players.game-646.json` 是唯一的游戏求解权威来源；当前为 646 条启用记录。
- `solver.js` 是纯函数严格求解层。浏览器与 Node 回归测试共用同一套规则，避免 UI 与测试各自解释颜色。
- 求解器保留游戏源数据的原始国籍、战队、位置和 `is_active` 布尔值；这些字段按游戏后端的原始精确比较，中文位置/状态仅用于展示，不能把不同源值意外合并。
- `app.js` 只负责读取截图、让用户校正颜色/箭头、展示候选和推荐下一猜。
- 截图历史走集合交集：所有已应用反馈都必须满足。它不会走相似度打分或“最像”的回退逻辑。
- 每条已应用反馈会先编译为谓词后再扫描 646 人题库；推荐探针只从严格候选集中选择，因此不会把已被颜色排除的教练或其他非候选重新推荐出来。
- 题库不能加载或少于 600 人时，页面显示错误并停止推荐；不会再回退到 65 人种子数据。

## 数据层约束

游戏字段为：昵称、国家、游戏赛区、战队、年龄、位置、Major 冠军、Major 参赛、状态、是否启用。任何未来的 HLTV 扩展字段（例如 Rating、地图、武器或比赛时间窗）只能作为单独缓存，不能覆写这些游戏字段，也不能改变截图颜色的解释。

当前仓库没有把“HLTV 全站历史数据”伪装成已完成的本地库。若后续加入合法获取的 HLTV 扩展，应按昵称/HLTV ID 关联到游戏选手，但严格求解仍固定使用游戏字段。

## 已知非目标

- 不读取、注入或自动操作对战网页；最终昵称仍由用户手动提交。
- 不用 OCR 决定昵称；用户从本地题库选择本行猜测，避免大小写、数字和特殊字符误识别。
- 不把黄色应用到战队、位置或状态。发现这种读数时页面会阻止应用并要求校正。

## 全题库规则审计

`tests/run-full-pool-contract-audit.js` 不使用 `solver.js` 来判定游戏反馈，而是独立复刻公开后端的 `compareGuess` 契约：队伍/位置原始精确相等、国籍按原始赛区判断、年龄黄色范围 3、两项 Major 黄色范围 1、状态按 `Boolean(is_active)` 相等。它对每一个反馈分区断言求解器返回的候选集合完全相等，并对每名猜测者的全绿分区断言昵称排除仍正确。

当前 646 人题库已用四个无重叠分片完成：417,316 个配对、84,175 个反馈分区全部通过。36 个“猜错昵称但七项属性全绿”的实际情形也被全量覆盖，因此界面不会再把属性全绿错误解释为昵称命中。
